> **Architecture First: как в одиночку с ИИ сделать альтернативу Jira** — Часть 14.
> В [предыдущей статье](telegram-login-widget-dotnet-auth) мы добавили вход, который работает в браузере. Теперь над досками появляется новый уровень — спейсы, которые группируют доски по проектам.

## Краткое содержание

Как мы сгруппировали доски по проектам в таск-трекере, не превратив модель данных в клубок nullable-колонок:

1. Добавили уровень группировки над доской. **Спейс** содержит много досок, доска — много issues. У спейса есть название и цвет (короткий ключ появился позже), и именно между спейсами переключается навигация.
2. Сначала повесили nullable `SpaceId` и на доску, и на issue, а через двенадцать дней оставили спейс только у **доски**, как обязательный внешний ключ. Теперь issue находит свой спейс через `Issue → Status → Epic → Space`, а перенос доски обновляет одну строку, а не каждую issue в ней.
3. Убрали состояние «доска без спейса»: у каждого пользователя есть спейс по умолчанию с доской Backlog, и каждый новый спейс создаётся сразу со своим Backlog.
4. Данные существующих пользователей перенесли прямо в миграции обычным SQL: один `insert … select` на уровень и один `update` для issues.
5. Строки по умолчанию пометили флагом `IsDefault` и запретили их удалять.
6. Весь код переноса между спейсами собрали в одном месте.

К этой форме мы пришли в три шага за двенадцать дней. Самое интересное — первая версия, которую мы почти сразу переписали.

## Почему одних досок было недостаточно

Мы разработчики Laraue Boards и одновременно одни из самых активных его пользователей. После нескольких недель ежедневной работы кое-что стало мешать. Доска (в коде — эпик) — это канбан-доска со своими колонками, и все они лежали одним плоским списком. Доски, связанные с личной жизнью, оказывались рядом с проектными, а мы хотели держать их раздельно.

Были варианты дешевле новой сущности:

- **Теги у доски.** Плоская структура без иерархии, и к ней нечего привязать в будущем при разграничении прав.
- **Отдельный аккаунт для работы.** Переключение аккаунтов — ровно то трение, которое мы хотели убрать.
- **Папки.** Это тот же спейс под другим названием, поэтому мы дали ему нормальное имя.

Идея не новая. В Confluence есть spaces, в Trello и Notion — workspaces, в Jira — projects, в Linear — teams. Мы выбрали **спейс**: именованную цветную группу досок, на которую переключаешься целиком. Словарь продукта стал таким: **Спейс → Доска → Issue**, а в коде доска — это `Epic`. В [документации](https://boards.laraue.com/ru/documentation) «доска» и «эпик» используются как синонимы.

## Подготовка: переименование и две маленькие таблицы (11–12 апреля)

До спейсов код был переименован в словарь, который вы видели в [части 9](issue-board-telegram-mini-app): `Card` стал `Issue`, `CardCategory` — `Epic`, `CardStatus` — `Status`. Это заняло две миграции 11 апреля (`RenameMainEntities` и `RenameEntitiesFks`), и сделать это стоило до того, как на старые названия начнёт наслаиваться что-то новое.

В те же выходные добавились две мелочи, которые пригодятся спейсам:

- `TouchedAt` у эпика — чтобы доски сортировались по последней активности в них.
- Таблица `UserPreferences`, по строке на пользователя, чтобы запоминать, чем он пользовался в последний раз. Текущий спейс будет храниться там.

## Первая версия: nullable SpaceId у доски и у issue (14 апреля)

Первые коммиты ([`dbe944d`](https://github.com/Laraue/Laraue.Apps.Boards/commit/dbe944d) и [`526bfbc`](https://github.com/Laraue/Laraue.Apps.Boards/commit/526bfbc)) добавили сущность `Space` и CRUD для неё:

```csharp
public class Space
{
    public long Id { get; set; }

    [MaxLength(128)]
    public required string Name { get; set; }

    [MaxLength(7)]
    public string? Color { get; set; }

    public Guid CreatorId { get; set; }
    public User? Creator { get; set; }

    public DateTime CreatedAt { get; set; }
    public DateTime UpdatedAt { get; set; }

    /// <summary>Epics linked to the space.</summary>
    public IList<Epic>? Epics { get; set; }
}
```

И `Epic`, и `Issue` получили ссылку на него:

```csharp
public long? SpaceId { get; set; }
public Space? Space { get; set; }
```

Пять миграций, написанных 13–14 апреля, показывают, как прошёл день:

| Миграция | Что сделала |
|---|---|
| `CreateSpaces` | таблица `spaces` |
| `CreateSpacePreference` | `space_id` в настройках пользователя: спейс, в котором он был в последний раз |
| `AddSpaceIdToEpic` | nullable `space_id` с индексом и внешним ключом в `epics` |
| `AddSpaceIdToIssue` | то же в `issues` |
| `MakeSpaceIdInPreferencesNullable` | у пользователя может быть ещё не выбран спейс |

Это была очевидная первая версия. Доска спейса — это запрос по issues, поэтому у каждой issue был собственный `SpaceId` рядом с эпиковым. Всё было nullable, потому что у существующих досок и issues спейса ещё не было, а nullable-колонка позволяет миграции пройти, не трогая данные.

Фронтенд подтянулся в тот же день. Всплывающее окно переключения спейсов (`LnbSpacePopup`) появилось 14 апреля, окна редактирования и удаления спейса — 17 апреля. Тексты добавлялись сразу на английском и русском (коммиты 17 апреля затрагивают оба файла локализации).

## Может ли внешний ключ быть nullable?

Да. В SQL столбец внешнего ключа может быть `NULL` — и в PostgreSQL, и в SQL Server, MySQL, SQLite: строка с `NULL` просто не проверяется по родительской таблице и означает «родителя нет». Поэтому настоящий вопрос не «можно ли?», а «существует ли в вашей предметной области состояние *родителя нет*?»

- **Nullable уместен, когда отсутствие — настоящее состояние.** В нашей модели issue, созданная в веб-приложении, не связана ни с каким сообщением Telegram, поэтому `Issue.TelegramMessageId` — это `long?`, и код, который его читает, ожидает `null`.
- **Nullable неверен, когда отсутствие — просто дыра в данных.** Доски без спейса в продукте не бывает: это доска, до которой ещё не дошла миграция, и каждому, кто читает эту колонку, приходится придумывать смысл для `null`.

Во втором случае сделайте ключ обязательным, а случаю «пока ничего нет» дайте строку: спейс по умолчанию — подход «строка по умолчанию» из части 9. Остальная статья — о том, как мы пришли к этому выводу, включая неверный поворот.

## Снова nullable-ключ, и что уже говорилось в части 9

В [части 9](issue-board-telegram-mini-app) есть целый раздел как раз про этот выбор: nullable внешний ключ или строка по умолчанию. Мы знали аргументы и всё равно пошли кратчайшим путём — он быстрее всего давал работающую версию. Каждый `space_id` был `bigint null`, а значит, любой код, который его читал, должен был отвечать на вопрос «что значит issue без спейса?», и честный ответ был — ничего.

23 апреля мы написали миграцию, которая убрала состояние «нет спейса». В сокращённом виде, только про спейсы, она выглядела так:

```sql
insert into spaces (name, color, creator_id, created_at, updated_at, organization_id, is_default)
select 'Default Space', '#50b3b3', o.owner_id, o.created_at, o.created_at, o.id, true
from organizations o
where o.type = 1;

insert into epics (name, user_id, color, created_at, touched_at, updated_at, organization_id, space_id, is_default)
select 'Backlog', s.creator_id, '#ff0000', s.created_at, s.created_at, s.created_at, s.organization_id, s.id, true
from spaces s;

update issues i
set space_id = s.id,
    organization_id = s.organization_id
from spaces s
where i.space_id is null and s.is_default = true and s.creator_id = i.user_id;
```

Это ядро миграции данных: один спейс по умолчанию на каждого пользователя, одна доска Backlog в каждом спейсе, и все существующие issues переехали под них. В полном скрипте было ещё несколько запросов. Первый из них создавал *личную* организацию для каждого пользователя — это та самая таблица `organizations` в первом `from` выше. К ней мы вернёмся в следующей статье.

Сам файл не дожил. Он был удалён тремя днями позже, в коммите, который перестроил схему, но правило, которое он выражал, осталось в коде.

## Итоговая форма: спейс живёт только у доски (26 апреля)

У коммита [`a095e69`](https://github.com/Laraue/Laraue.Apps.Boards/commit/a095e69) скромное сообщение — «app is now closer to target org DB schema» — и большой diff: 23 файла, 1457 добавленных и 341 удалённая строка. Основную работу сделали две его миграции. В терминах модели:

```diff
 public class Epic
 {
-    public long? SpaceId { get; set; }
+    public long SpaceId { get; set; }
 }

 public class Issue
 {
-    public long? EpicId { get; set; }
-    public long? SpaceId { get; set; }
-    public long? StatusId { get; set; }
+    public long StatusId { get; set; }
 }
```

Спейс стал **обязательным у доски**, а issue лишилась и `EpicId`, и `SpaceId`. Теперь issue знает ровно одно — свой статус. Статус принадлежит эпику, эпик принадлежит спейсу:

```
Issue → Status → Epic → Space
```

В EF Core фильтр по спейсу — это проход по этой цепочке. Две настоящие строки из бэкенда:

```csharp
query = query.Where(i => i.Status!.Epic!.Space!.Key == spaceKey);
```

```csharp
.Where(x => x.Status!.Epic!.Space!.OrganizationId == issueData.OrganizationId)
```

Цена — несколько join'ов. Выгода — ровно одно место, которое говорит, где живёт issue. Перенос доски в другой спейс — это обновление одной строки `epics`, а не переписывание `space_id` у каждой issue в ней, и два значения никогда не разойдутся, потому что второй копии нет.

Днём раньше, 25 апреля, у спейсов и досок появился флаг `IsDefault`. Вместе с обязательным внешним ключом он дал итоговое правило: **всегда есть спейс и всегда есть доска, в которую можно положить issue.**

## Строки по умолчанию в коде

То же правило есть в коде, который создаёт спейс. Каждый новый спейс создаётся вместе со своей доской Backlog, одним `SaveChanges`:

```csharp
var entity = new Space
{
    CreatorId = creatorId,
    Name = name,
    Color = color,
    CreatedAt = dateTime,
    UpdatedAt = dateTime,
    Key = key.ToUpper(),
    OrganizationId = organizationId,
    Epics = new List<Epic>
    {
        OrganizationDefaults.GetNewBacklogEpicEntity(creatorId, dateTime)
    }
};

context.Spaces.Add(entity);
```

Backlog создаётся с `IsDefault = true` (см. [`CoreSpacesService.cs`](https://github.com/Laraue/Laraue.Apps.Boards/blob/main/src/Laraue.Apps.Boards.Services/CoreSpacesService.cs)). Спейс по умолчанию и Backlog по умолчанию нельзя удалять: иначе «всегда есть куда положить issue» перестаёт быть правдой, как только кто-то их удалит. В мае мы поправили места, где API всё ещё сообщал, что такие сущности можно удалить (коммит 11 мая), и запретили выдавать право на удаление для них (12 мая), каждый раз с тестом.

## Перенос issues и досок между спейсами

Первый интерфейс переноса был написан 16 апреля, через два дня после самих спейсов: модальное окно для переноса issue с двумя списками внутри — для доски и для спейса. 19 и 20 мая логика переноса была переписана в одно место вместе с тестовым классом для массового переноса. К тому времени видов переноса было три (issue на другую доску, доска в другой спейс и спейс целиком), и три копии одной логики непременно бы разошлись.

Продуктовое правило, которое из этого получилось, простое, и [документация](https://boards.laraue.com/ru/documentation) его описывает: спейс доски задаётся при её создании и дальше не меняется. Перенос спейса или доски со всем содержимым — отдельное осознанное действие, которое переносит их между организациями.

## Удаление спейса

Удаление прошло три версии: окно 17 апреля, переписанная логика 4 июня и в сентябре — мягкое удаление. Сегодня спейс помечается удалённым вместе со всем, что ниже, в одной транзакции, чтобы ничего не оставалось привязанным к несуществующему спейсу. Метод идёт по той же цепочке, что и запросы выше, снизу вверх:

```csharp
await using var transaction = await context.Database.BeginTransactionAsync(cancellationToken);

var epicIds = context.Epics.Where(x => x.SpaceId == id).Select(x => (long?)x.Id);
var statusIds = context.Statuses.Where(x => epicIds.Contains(x.EpicId)).Select(x => (long?)x.Id);

await context.Issues
    .Where(x => statusIds.Contains(x.StatusId))
    .ExecuteUpdateAsync(u => u
        .SetProperty(p => p.DeletedAt, deletedAt)
        .SetProperty(p => p.DeletedByUserId, deleterId), cancellationToken);

// дальше такое же обновление для статусов, эпиков и в конце самого спейса

await transaction.CommitAsync(cancellationToken);
```

Четыре вызова `ExecuteUpdateAsync` вместо загрузки чего-либо в память, а транзакция делает их единым целым. Тест, который это фиксирует, называется так, как заслуживает: `User_ShouldSoftDeleteSpaceAndAllDescendants_WhenSpaceIsDeleted`.

## Выводы

- **Ставьте связь на самый узкий уровень, который может её нести.** Спейс принадлежит доске. Issue получает его бесплатно, а перенос остаётся операцией над одной строкой.
- **Строка по умолчанию лучше null.** Каждый nullable-ключ — это вопрос, на который каждый читатель данных должен отвечать заново. «У каждого пользователя есть спейс, а у каждого спейса есть Backlog» — это инвариант, который можно протестировать.
- **Миграция данных — часть функциональности.** Несколько десятков строк SQL решали, откроют ли существующие пользователи приложение и увидят ли свои доски, и их стоило писать и перечитывать так же внимательно, как модель.
- **Меняйте форму схемы рано.** Модель менялась три раза за двенадцать дней. Это было дёшево, пока в приложении было несколько пользователей, и дорого даже представить спустя несколько месяцев.

Если вам интересно, как мы называем интеграционные тесты, загляните в [`SpacesControllerTests.cs`](https://github.com/Laraue/Laraue.Apps.Boards/blob/main/tests/Laraue.Apps.Boards.IntegrationTests/SpacesControllerTests.cs): каждый тест говорит, кто что делает и при каком условии.

Спейсы ответили на один вопрос: «моё или проектное». Миграция выше уже намекает на следующий: ей пришлось создавать для каждого пользователя *личную* организацию, потому что спейс будет принадлежать не только одному человеку.
