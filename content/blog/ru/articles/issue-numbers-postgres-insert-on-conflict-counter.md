> **Architecture First: как в одиночку с ИИ сделать альтернативу Jira** — Часть 18.
> В [предыдущей статье](access-control-without-roles-task-tracker-permissions) мы разобрали права доступа. Когда в организации работает несколько человек, им нужно как-то ссылаться на задачи друг друга, а внутренний `id` трудно произнести и запомнить.

## Краткое содержание

Как у задач в Boards появились короткие ключи:

1. Сначала решили, как будут выглядеть ссылки, чтобы потом их не ломать: `/organizations/{организация}-{суффикс}/issues/{ключ спейса}-{номер}`.
2. Адрес организации — это slug, который выбирает пользователь, и случайный суффикс из четырёх символов. По адресу нельзя занять чужое название или проверить, есть ли организация.
3. У каждого спейса есть ключ из трёх символов, уникальный среди живых спейсов организации. Ключ удалённого спейса можно занять снова.
4. Номера issues в спейсе идут подряд: 1, 2, 3 и так далее. Последний выданный номер хранится в таблице-счётчике и увеличивается одним запросом `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`.
5. При переносе доски в другой спейс её issues получают новые номера в этом спейсе.

## Сначала — как будут выглядеть ссылки

Пока у задачи нет понятного имени, ссылку на неё можно только скопировать из адресной строки. Нам нужны были номера задач, и мы не стали изобретать своё, а взяли подход Jira: `BRD-42`, где `BRD` — ключ спейса, а `42` — номер задачи в нём.

Но прежде чем делать номера, нужно было решить, как будет выглядеть полная ссылка на задачу. Ссылки начинают жить своей жизнью: их отправляют в чаты, вставляют в другие задачи и документы. Если формат поменять после того, как ссылки уже разошлись, все они перестанут работать. Поэтому адреса организаций появились раньше номеров задач.

## Адрес организации: slug и случайный суффикс

Первое, что приходит в голову, — сделать адресом организации её название: `/organizations/laraue`. У такого варианта две проблемы. Любой может создать организацию с чужим названием и занять адрес, к которому не имеет отношения. И по адресу можно проверить, существует ли организация: например, есть ли в Boards организация `laraue`.

Поэтому адрес состоит из двух частей: slug, который выбирает пользователь, и случайного суффикса из четырёх символов, который генерирует приложение.

```csharp
/// <summary>
/// Organization slug. The public name to access this organization.
/// </summary>
[MaxLength(64)]
public string Slug { get; set; } = string.Empty;

/// <summary>
/// Postfix to allow slugs be ununique and make it harder to access something else organization.
/// </summary>
[MaxLength(4)]
public string SlugPostfix { get; set; } = string.Empty;
```

Slug не обязан быть уникальным: две организации могут называться `laraue`, но адреса у них будут разные, например `laraue-a1B2` и `laraue-x7Kq`. Угадать чужой адрес по названию нельзя, а занимать названия бессмысленно.

## Ключ спейса

Ключ спейса — три символа, которые пользователь задаёт при создании спейса, например `BRD`. Приложение приводит его к верхнему регистру. Ключ должен быть уникальным внутри организации, но только среди спейсов, которые не удалены: спейсы удаляются мягко, и ключ удалённого спейса можно занять снова. Для этого в базе есть частичный уникальный индекс:

```csharp
modelBuilder.Entity<Space>()
    .HasIndex(x => new { x.OrganizationId, x.Key })
    .IsUnique()
    .HasDatabaseName(Constraints.SpaceKeyIndexName)
    .HasFilter("deleted_at IS NULL");
```

С этим индексом была история уже в продакшене. В логах мы нашли ошибку `500` при создании спейса: `duplicate key value violates unique constraint "ix_spaces_organization_id_key"`. Сервис не проверял, свободен ли ключ, и полагался только на индекс, поэтому пользователь получал ошибку сервера вместо понятного сообщения.

Исправление состоит из двух частей. Перед сохранением сервис проверяет, что среди живых спейсов организации такого ключа нет. А если два запроса с одним ключом придут одновременно, проверку пройдут оба, и второй упадёт уже на индексе. Поэтому нарушение уникальности (код ошибки PostgreSQL `23505`) с именем этого индекса тоже превращается в ту же ошибку валидации.

Тогда же нашлась вторая ошибка. Поиск по issues строил словарь спейсов по ключу и не исключал удалённые спейсы. Когда удалённый и живой спейс в одной организации получили одинаковый ключ, словарь падал на дубликате, и вместе с ним падал весь поиск.

## Номер issue: почему не последовательность

У PostgreSQL есть готовый механизм для номеров — последовательности (`sequence`). Но последовательность допускает пропуски: если транзакция, которая взяла номер, откатилась, этот номер уже не вернётся. Мы хотели, чтобы номера в спейсе шли подряд, без дыр.

Поэтому последний выданный номер хранится в отдельной таблице, по одной строке на спейс:

```csharp
public class SpaceCounter
{
    public long SpaceId { get; set; }
    public int LastNumber { get; set; }
}
```

Следующий номер выдаёт один запрос:

```sql
INSERT INTO space_counters (space_id, last_number)
VALUES ({0}, {1})
ON CONFLICT (space_id) DO UPDATE
SET last_number = space_counters.last_number + {1}
RETURNING last_number
```

Если строки для спейса ещё нет, запрос её создаёт. Если есть — увеличивает `last_number` и возвращает новое значение. Так не нужно отдельно проверять, существует ли счётчик, а значит, нет и гонки между проверкой и вставкой.

Запрос выполняется внутри той же транзакции, что и создание issue:

```csharp
private async Task<int> GetLastNumber(long spaceId, int count, CancellationToken cancellationToken)
{
    context.Database.EnsureTransactionStarted();

    var query = FormattableStringFactory.Create(SqlQuery, spaceId, count);
    var result = await context.Database
        .SqlQuery<int>(query)
        .ToListAsyncEF(cancellationToken);

    return result.First();
}
```

Именно это и убирает пропуски. `UPDATE` блокирует строку счётчика до конца транзакции, поэтому второй запрос на номер в том же спейсе ждёт, пока первый закончится. Если транзакция откатилась, увеличение счётчика откатывается вместе с ней, и следующая issue получит тот же номер. Цена — issues одного спейса создаются по очереди, но для таск-трекера это незаметно.

Второй параметр, `count`, позволяет зарезервировать сразу несколько номеров. Он нужен при переносе доски, о котором ниже. В первой версии метод, который возвращает первый номер из зарезервированного диапазона, ошибался на единицу (`last - count + 2` вместо `last - count + 1`). Её нашли и исправили вместе с тестами на массовый перенос.

## Номера для уже созданных issues

К моменту, когда появились номера, у пользователей уже были issues. Миграция пронумеровала их внутри каждого спейса в порядке создания и записала в счётчики последний номер:

```sql
WITH issue_counters as (
    select i.id, e.space_id, row_number() over (partition by e.space_id order by i.id) as number from issues i
    inner join statuses s on i.status_id = s.id
    inner join epics e on s.epic_id = e.id
    order by i.id
)
insert into issue_numbers
select ic.id, ic.space_id, ic.number
from issue_counters ic;
```

В первой версии миграции в `row_number()` не было `order by i.id`. Без него PostgreSQL нумерует строки в произвольном порядке, и старые задачи могли получить номера вперемешку. Обе ошибки мы нашли, когда спрашивали ИИ, что произойдёт в разных случаях, и исправили одним коммитом.

## Перенос доски в другой спейс

Номер issue — это номер внутри спейса. Когда доска переезжает в другой спейс, её issues получают новые номера в нём: сервис резервирует в счётчике нового спейса столько номеров, сколько issues переезжает, и раздаёт их по порядку.

Старый ключ после переноса перестаёт работать. Перенаправления со старого ключа на новый пока нет: досками переезжают редко, а добавить перенаправление будет несложно, когда оно понадобится.

## Итоги

- **Формат ссылок решили заранее.** Адреса организаций появились раньше номеров задач, чтобы ссылки не пришлось ломать потом.
- **Адрес организации нельзя занять.** Slug выбирает пользователь, а случайный суффикс делает адрес уникальным и не даёт угадать чужой.
- **Ключ спейса уникален среди живых спейсов.** Это обеспечивает частичный уникальный индекс, а гонку при создании закрывает обработка ошибки `23505`.
- **Последовательные номера.** Вместо последовательности PostgreSQL — таблица-счётчик и `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` внутри транзакции создания issue.
- **Перенос меняет номера.** Перенаправления со старых ключей пока нет.
