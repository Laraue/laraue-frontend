> **Architecture First: как небольшой командой с ИИ сделать альтернативу Jira** — Часть 9.
> В [предыдущей статье](telegram-mini-app-authentication-dotnet) у приложения появился бэкенд с авторизацией. В этой мы делаем первую настоящую функцию — домен issues — и проектируем для него базу данных.

Домен issues — это часть приложения, которая отвечает за задачи, их статусы и эпики и позволяет управлять ими через веб-интерфейс. Как сделать CRUD для задач, разбирать не будем: исходный код открыт, да и гайдов в сети полно. Расскажем об одной практической проблеме при проектировании схемы БД: как представить issue, который не входит ни в один эпик. Очевидный ответ — сделать внешний ключ `StatusId` nullable, с этого мы и начали. Но позже это сильно усложнило весь код, и ниже мы подробно разберём почему.

## Модели Issue, Status и Epic

Issue — это карточка на доске, которую бот создаёт из сообщения. Её можно создать и напрямую через веб-интерфейс:

```csharp
public class Issue
{
    public long Id { get; set; }

    [MaxLength(4096)]
    public required string? Content { get; set; }

    public DateTime CreatedAt { get; set; }
    public DateTime UpdatedAt { get; set; }

    public Guid UserId { get; set; }
    public User? User { get; set; }

    public long StatusId { get; set; }
    public Status? Status { get; set; }

    public TelegramMessage? TelegramMessage { get; set; }
    public long? TelegramMessageId { get; set; }
}
```

Ключевая связь — `StatusId`: issue всегда находится в каком-то статусе, а статус всегда связан с какой-то доской (то есть эпиком). То есть `Status` — это одна колонка на доске:

```csharp
public class Status
{
    public long Id { get; set; }

    [MaxLength(128)]
    public string Name { get; set; } = string.Empty;

    [MaxLength(7)]
    public string Color { get; set; } = string.Empty;

    public long EpicId { get; set; }
    public Epic? Epic { get; set; }

    public int SortOrder { get; set; }

    public IList<Issue>? Issues { get; set; }
}
```

Статус принадлежит эпику через `EpicId`. Цепочка получается такая: `Issue → Status → Epic` — issue не ссылается на свой эпик напрямую, а добирается до него через статус.

## Nullable внешний ключ или строка по умолчанию?

Большинство issue находятся в каком-то эпике, но в приложении есть и бэклог, где задачи ещё не относятся ни к одному эпику. Значит, схема БД должна позволять создать issue без эпика, и сделать это можно двумя способами.

### Первый способ: сделать внешний ключ nullable.

В бэклоге у задач нет статуса, поэтому у issue могло бы быть nullable-поле `StatusId`, где `null` означает бэклог. С этого мы и начали.

На практике такой подход принёс немало проблем. Когда `null` означает не «нет значения», а «бэклог», об этом должен помнить каждый кусок кода. В коде множатся ветки `if (StatusId == null) || …`, и каждый раз приходится решать, нужна ли отдельная логика или валидация, если в поле статуса `null`. Словом, каждой новой функции, которая работает с issue, приходится заново обрабатывать случай с `null`.

Вторая проблема: бэклог нельзя настроить. В интерфейсе бэклог отчасти ведёт себя как обычный эпик (его можно переименовать, поменять цвет), а nullable-модель не даёт сделать это аккуратно: либо заводить отдельную таблицу, которая дублирует поля `epics`, и ветвить логику в бизнес-слое, либо смириться с тем, что бэклог не настраивается.

### Второй способ: строка по умолчанию.

При создании пользователя в базу добавляется **эпик по умолчанию** с **одним статусом по умолчанию**. То есть бэклог — это эпик с флагом `IsDefault` в модели:

```csharp
public class Epic
{
    public long Id { get; set; }

    [MaxLength(128)]
    public required string Name { get; set; }

    public Guid UserId { get; set; }
    public long SpaceId { get; set; }

    public bool IsDefault { get; set; }
    public IList<Status>? Statuses { get; set; }
    // ... временные метки
}
```

При таком подходе труднее допустить серьёзную ошибку, например показать задачи из бэклога чужому пользователю. Но и у него есть цена. Эпик по умолчанию должен быть у каждого пользователя, и его создание нужно гарантировать — мы создаём бэклог при регистрации. Кроме того, без ветвлений вроде «если эпик — бэклог, удалять его нельзя» (и на бэкенде, и на фронтенде) не обойтись. Но такие ветвления есть только в тех немногих местах, где бэклог и обычные эпики должны вести себя по-разному, и не расползаются по всем сервисам.

С тех пор nullable внешний ключ мы используем, только когда `null` действительно означает, что связи нет: сотрудник без руководителя в `manager_id`, заказ без назначенного курьера. Даже если nullable-колонка кажется удачным решением, с ростом функциональности может появиться случай, который так обработать трудно.

### Избыточность данных или дополнительный join

Из-за цепочки `Issue → Status → Epic` базе, чтобы найти эпик issue, приходится делать join: `issues → statuses → epics`. Этого можно избежать, если хранить `EpicId` прямо в issue, — к такой оптимизации иногда прибегают, чтобы ускорить чтение.

Мы не стали оптимизировать заранее: лишнее поле означает, что данные в базе дублируются и их нужно правильно обновлять, а это источник багов. При нынешних объёмах лишний join проблем не создаёт, а вот ловля таких багов могла бы отнять у разработчиков много времени.

## Бэкенд: контроллеры, сервисы уровня Host, сервисы уровня Core

На бэкенде мы стараемся держаться многослойной архитектуры. Проще всего показать это на примере — создании issue.

Запрос принимает тонкий [`IssuesController`](https://github.com/Laraue/Laraue.Apps.Boards/blob/main/src/Laraue.Apps.Boards.WebApiHost/Controllers/IssuesController.cs). Все его эндпоинты требуют авторизации — контроллер помечен атрибутом `[Authorize]`. Каждый метод контроллера только добавляет к запросу данные пользователя из `HttpContext.User` и передаёт его сервису уровня Host [`IssuesService`](https://github.com/Laraue/Laraue.Apps.Boards/blob/main/src/Laraue.Apps.Boards.WebApiServices/IssuesService.cs):

```csharp
public interface IIssuesService
{
    Task<ColumnIssues[]> GetBoard(
        GetBoardRequest request,
        CancellationToken cancellationToken);

    Task Delete(DeleteIssueRequest request, CancellationToken ct);
    Task<long> Create(CreateIssueRequest request, CancellationToken ct);
    Task Update(UpdateIssueRequest request, CancellationToken ct);

    Task<IssueDetailDto> GetIssue(
        GetIssueRequest request,
        CancellationToken cancellationToken);
}
```

Сервис проверяет права вызывающего, валидирует данные, при необходимости открывает транзакцию и маппит данные. Сам он не создаёт, не меняет и не удаляет записи в базе — это делает сервис уровня Core [`ICoreIssuesService`](https://github.com/Laraue/Laraue.Apps.Boards/blob/main/src/Laraue.Apps.Boards.Services/CoreIssuesService.cs), в котором собрана общая логика изменений:

```csharp
public interface ICoreIssuesService
{
    Task<long> Create(
        CreateIssueRequest request,
        CancellationToken cancellationToken);

    Task Update(
        long issueId,
        Action<UpdateSettersBuilder<Issue>> setters,
        CancellationToken cancellationToken);

    Task Delete(
        long id,
        CancellationToken cancellationToken);
}
```

В итоге при создании issue запрос проходит такой путь: контроллер → host-сервис (проверка прав, открытие транзакции) → core-сервис (запись строки).

### Разделение ответственности между Host и Core сервисами

**Core-сервис** прячет сложную логику, которая нужна в нескольких местах. Сервис уровня Host просто вызывает обновление issue и не думает о том, что вместе с `Issue` нужно обновить `TouchedAt` у его эпика или добавить запись в историю изменений.

Разделение нужно потому, что core-сервисы используют оба хоста, web API и Telegram. Issue можно изменить и из Telegram-чата, и из веб-интерфейса, и в обоих случаях изменение должно обрабатываться одинаково правильно. Так мы не дублируем код и при этом оставляем хостам свободу (например, валидировать по-разному).

### Проверка прав доступа

Пока права устроены просто: пользователь может читать и менять только свои issue и эпики. Но в будущем появится режим организаций, поэтому методы, которые возвращают доступные пользователю сущности, мы вынесли в отдельный класс [`AccessService`](https://github.com/Laraue/Laraue.Apps.Boards/blob/main/src/Laraue.Apps.Boards.Services/AccessService.cs) — так потом будет меньше рефакторинга:

```csharp
public interface IAccessService
{
    Task<T> GetAvailableEpics<T>(
        Guid userId,
        Func<IQueryable<Epic>, Task<T>> map,
        CancellationToken cancellationToken);

    Task<T> GetAvailableIssues<T>(
        Guid userId,
        Func<IQueryable<Issue>, Task<T>> map,
        CancellationToken cancellationToken);

    Task<bool> CanMoveToStatus(
        Guid userId, long statusId, CancellationToken cancellationToken);

    Task<bool> CanModifyStatus(
        Guid userId, long statusId, CancellationToken cancellationToken);
}
```

`GetAvailableEpics` и `GetAvailableIssues` принимают `userId` и функцию `map`, которая проецирует доступные пользователю сущности. Host-сервис сам решает, что с ними делать (посчитать, спроецировать, достать строку), и в принципе не может получить `IQueryable` с чужими объектами.

### Транзакции

Транзакцией всегда управляет host-сервис: только он знает, когда операция завершена целиком. Можно было бы обойтись без этого правила и использовать вложенные транзакции или счётчик транзакций в приложении. Но на практике проще задать ограничения в архитектуре, чем потом упереться в ограничения инфраструктуры (например, вложенные транзакции поддерживают не все БД).

Хотя транзакцией управляет host-сервис, бывает, что core-сервису атомарность нужна независимо от того, кто его вызвал, — например, когда он пишет сразу в несколько таблиц. Полагаться вслепую на то, что вызывающий уже открыл транзакцию, он не может. Поэтому core-сервис вызывает `EnsureTransaction`: если host не открыл транзакцию, выбрасывается исключение.

## Из HTML-прототипа от AI в Vue-компоненты

Когда API готов, фронтенд может показывать настоящие данные. Дизайн мы сгенерировали ещё в [начале цикла](prototyping-ui-with-ai-before-code), но это был только HTML-макет. Пора превратить его в настоящие компоненты.

Вообще, ИИ может разбить файл макета на компоненты самостоятельно, но мы в основном делали это вручную: смотрели на сгенерированную разметку и просили ИИ сделать один компонент из конкретного куска кода. Повторяющийся `<div class="card">` — компонент `Card`, повторяющаяся обёртка колонки — `Column`.

Все компоненты сразу мы не просили, потому что хотели контролировать процесс. Огромный pull request невозможно внимательно проверить, в нём останутся ошибки, которых мы даже не заметим. Когда выносишь по одному компоненту, каждый шаг маленький и его легко проверить. Получившийся результат можно увидеть в [папке компонентов](https://github.com/Laraue/laraue-boards/tree/master/app/components).

### Клиенты API на фронтенде

Каждому контроллеру бэкенда соответствует composable-клиент на фронтенде, в том же стиле, что и `userApi` из прошлой статьи. У эпиков — [`epicsApi.ts`](https://github.com/Laraue/laraue-boards/blob/185cc189361ba9345913226c10616ab015e958b4/app/composables/epicsApi.ts), у issues свой.

Пишем мы их вручную. Можно было бы генерировать клиенты из документа OpenAPI/Swagger, тогда типы фронтенда автоматически совпадали бы с бэкендом. Но пришлось бы потратить время, чтобы код генерировался в нужном нам виде. Пока API небольшой, мы остановились на ручном варианте.

### Пара слов об applyInsets: вписываем приложение в рамку Telegram

Когда мы открыли приложение как Telegram Mini App, оказалось, что часть его закрывают элементы интерфейса самого Telegram. Для таких случаев Telegram отдаёт *insets* — отступы, которые показывают, сколько места по краям занимает его интерфейс. Приложение применяет их в [`app.vue`](https://github.com/Laraue/laraue-boards/blob/master/app/app.vue) через шаг `applyInsets`, добавляя layout'у внутренние отступы.

Одни insets проблему до конца не решают: если применять их с запасом, как описано в документации, на экране остаются большие пустые области, а если без запаса — кнопки управления Mini App наезжают на интерфейс приложения. В итоге мы определяем, что приложение запущено внутри Telegram, и отдельно правим CSS под этот случай. Отлаживали мы это локально: добиться аккуратной отрисовки может занять много времени.

## Итоги

Веб-приложение показывает на доске issues пользователя, которые приходят с бэкенда после аутентификации. Issue можно создавать, двигать между статусами и удалять, каждый пользователь работает только со своими данными. Реализацию CRUD строка за строкой мы не разбирали — код есть в репозиториях ([бэкенд](https://github.com/Laraue/Laraue.Apps.Boards), [фронтенд](https://github.com/Laraue/laraue-boards)).

Пора было показать приложение людям и узнать, что они о нём думают на самом деле. Мы рассказали о нём в своих Telegram-каналах, написали в Threads короткое описание продукта для тех, кто о нём не слышал, и попросили друзей в личных сообщениях его попробовать. Хотелось посмотреть, как реальные люди пользуются приложением, и понять, что в нём работает, а что нет.
